# 自驾等时圈 H5

部署路径：`/isochrone/`

## 功能

- 桌面端 / 手机端响应式布局
- 输入地点搜索并定位
- 使用浏览器当前位置
- 10–60 分钟自驾等时圈
- 多层时间圈与地图图例
- **无需 API Key，无需注册第三方账号**

## 技术栈

- GitHub Pages（纯静态前端）
- MapLibre GL JS
- OpenFreeMap vector tiles（OpenStreetMap 数据）
- Nominatim（地点搜索；仅在用户主动提交搜索时请求，无自动补全）
- Valhalla 开源路由引擎的 FOSSGIS 公共 Demo 服务（自驾等时圈）

## 算法与服务说明

Valhalla 基于 OpenStreetMap 道路网络执行路由图搜索，并由 isochrone 服务输出指定驾驶时间内的可达区域 GeoJSON。前端直接请求公开服务，因此不需要用户输入密钥。

公共 Demo 服务适合个人、小规模和演示用途，并受 fair-use / rate limit 约束。如果后续访问量较大，应自行部署 Valhalla 服务。

## 使用

1. 访问 https://sschizoo.github.io/isochrone/
2. 输入地点或使用当前位置。
3. 选择驾驶时间。
4. 点击“生成自驾等时圈”。

> Nominatim 与 Valhalla 公共服务均应低频、合理使用。面向大规模正式业务时建议自托管相关开源服务。


## 自由时长与 30 天上限

当前版本支持用户直接输入数值并选择分钟、小时或天，最大 30 天。

- 1–60 分钟：调用 Valhalla 公共服务生成真实道路网络等时圈。
- 超过 60 分钟：由于公共 Valhalla 服务端对单条时间 contour 有硬限制，前端自动切换为“长时程估算”并使用虚线边界明确区分，避免把近似范围误标为精确道路等时圈。
- 如需 2 小时以上仍保持真实道路网络精确计算，需要自托管 Valhalla 并调整 service_limits，同时还要评估超大范围图搜索的计算成本。


## 真实道路网络模式（2026-09-27）

前端不再生成任何基于平均速度的圆形/近似范围。现在只有两类真实道路网络引擎：

1. 默认公共 Valhalla：无需 API Key，支持 1–60 分钟。
2. 自建 GraphHopper：无需 API Key，前端允许请求到 30 天；实际可计算范围取决于后端已导入的 OSM 路网、内存和 CPU。

在 `isochrone/router-config.js` 中设置 `graphhopperBaseUrl` 后，所有时长都会优先走自建 GraphHopper。

> 30 天的最短路径树可能遍历极大的道路图。它在算法意义上仍是真实道路网络结果，但计算成本可能非常高；需要按实际 OSM 数据覆盖范围和服务器硬件配置资源。


## 道路形状外推 Demo 算法

为了在 GitHub Pages 上演示超过公共 Valhalla 60 分钟限制的长时程等时圈，前端加入“道路形状外推”模式：

1. 先用 Valhalla 计算真实 60 分钟 OSM 道路网络等时圈。
2. 对 60 分钟边界每个顶点计算其相对起点的测地线距离和方位角。
3. 根据目标驾驶时长使用分段非线性扩张函数放大测地线距离。
4. 按原方位角重新投影边界顶点，从而保留当地真实道路等时圈的方向性、不规则轮廓和高速通道形态。
5. 60 分钟以上结果在 UI 中明确标记为“道路形状外推 · Demo”，仅用于视觉演示，不用于导航或工程分析。

该算法不再绘制简单圆形，因此视觉边界会明显更接近真实道路等时圈。


## 多波次道路传播 + 方向拟合（Demo v6）

长时程 Demo 不再单纯放大一条 60 分钟边界。

算法流程：

1. 第 1 波：从起点计算真实 15/30/45/60 分钟 Valhalla 道路等时圈。
2. 从 60 分钟联合边界按方位角抽取最多 5 个前沿点。
3. 第 2 波：每个前沿点分别再请求真实 60 分钟道路等时圈，并用 Turf.js `union` 与上一波可达区域合并，得到约 120 分钟传播范围。
4. 第 3 波同理，得到约 180 分钟传播范围。
5. 对 15/30/45/60/120/180 分钟的真实/拼接边界按 72 个方位扇区提取最大道路传播半径。
6. 目标时长落在观测时间之间时做方向逐扇区插值；超过实算时间时，对每个方向单独做幂律增长拟合，并限制指数和最大半径，生成清晰、连续的演示边界。
7. 公共 Valhalla 请求并发限制为 2，前沿点限制为 5，真实传播最多 3 波，避免为了 30 天演示产生数千次公共请求。

该结果仍属于 Demo 近似，但相比“单一 60 分钟轮廓整体缩放”，它实际采样了多轮真实道路扩散，因此能更好地反映高速路走廊、路网稠密度和方向差异。


## 最终圈真实请求包络（Demo v7）

当前固定输出 4 个最终圈（目标总时长的 25% / 50% / 75% / 100%）。

原则：**拟合只负责决定去哪里发请求；每个最终圈都必须由真实 Valhalla 请求参与生成。**

长时程最终圈流程：

1. 使用已有真实道路样本，对“目标时刻 - 60 分钟”的前沿进行方向拟合。
2. 计算该拟合前沿的真实几何周长。
3. 按周长等距抽取前沿点，默认约每 90 km 一个点；最少 6 个、最多 24 个。前沿点数不再固定为 5。
4. 每个前沿点分别向 Valhalla 请求真实 60 分钟道路等时圈，并发限制为 2，带轻微请求间隔。
5. 将截至该目标时刻的所有真实服务返回边界转换为 96 个方向的最大道路传播半径，形成连续外包络。
6. 最终显示的圈来自这些真实服务边界的外包络；拟合前沿本身不会直接进入最终显示结果。

这样既控制了公共服务调用规模，又保证四个最终圈都经过真实路网服务计算；边界长度越大，实际选取的前沿点越多。
